# Gemini Context: Paradox Script Formatter

## Project Overview
This project is a VS Code extension (`f1r3pr1nc3.paradox-formatter`) that provides formatting and logical optimization for Paradox Interactive game scripts (Stellaris, HOI4, EU4, CK2, etc.). It aims to provide smart indentation, block expansion, and syntax protection while simplifying complex logical expressions.

## Key Components
- `bin/logic_optimizer.py`: The core Python script responsible for parsing and optimizing Clausewitz logic. It handles De Morgan's laws, double negation removal, and NAND simplifications. It uses a custom tokenizer and parser to handle the unique structure of Paradox scripts.
- `out/extension.js`: The compiled VS Code extension entry point that interfaces with the Python backend.
- `syntaxes/`: Contains TextMate grammars (`.tmLanguage.json`) for various Paradox games to provide syntax highlighting.
- `test/`: Contains test event files for verification.

## Coding Standards
- **Indentation**: Strictly use tabs (literal `	`) for indentation in all code files (Python, JavaScript, TypeScript).
- **Python**:
    - Follow established patterns in `logic_optimizer.py` for regex and node manipulation.
- **TypeScript/JavaScript**: Standard VS Code extension development practices (using tabs).
- **Paradox Script**: The formatter itself enforces specific styles, such as lowercasing certain keywords (ROOT, PREV, etc.) and upperpasing logical operators (OR, AND, NAND, NOR).

## Domain Specific Knowledge (Clausewitz Scripting)
- **Existential Quantifiers**: `any_` and `count_` triggers act as existential quantifiers.
- **Logical Negation Rules**:
    - `NOT = { any_scope = { ... } }` is **NOT** equivalent to `any_scope = { NOT = { ... } }`.
    - Negations (NOT) cannot be pushed into existential quantifier scopes because `¬∃x` (It is not the case that there exists an x such that...) is not equivalent to `∃¬x` (There exists an x such that it is not the case that...).
    - This is a critical rule for the `logic_optimizer.py` to avoid breaking game logic.
- **Logic Optimization**: The formatter can simplify `OR-AND` structures into `NAND` and similar logical transformations to improve readability and potentially performance in-game.

## Known State & Recent Fixes
- The `logic_optimizer.py` horizontal merging step was updated to prevent merging structural block keywords (like `limit`, `trigger`) into `NOR` logic gates during numerical/boolean negation routines.
- The `logic_optimizer.py` was updated to replace regex-based logic with a proper parser to handle `factor=0` modifiers and nested blocks without corrupting the file structure (preventing unbalanced braces).
- Indentation preference for the workspace is set to 4-space tabs.
- The beta conditional conversions (`CONDITIONAL_CONVERSIONS`, `--conditional-conversions`) fold a `break = yes` dispatch chain and an `else` that only wraps one `if`/`else_if`/`else` chain into a single flat chain, and turn an `if`/`if` pair whose limits negate each other into `if`/`else_if`, and collapse an `if` with an empty body plus the `else` behind it - into one `OR` in trigger script (`L OR B`), and into one `if` with the negated limit in an effect (`machine_age_crisis_events.txt` line 3571), where `L OR B` would not even be effect script. The effect spelling needs the scope: the empty-if loop runs for `scope_context in (None, 'trigger', 'effect')` while the trigger rewrites inside it bail out on `'effect'`, and `body_hint` is scanned over the else body alone - a limit always looks like trigger script, so including it would make every pair look like a trigger. All of them step over interleaved comment lines and keep every comment in place - a comment on the `break` line itself moves onto the script in front of it (or becomes a comment line behind it when that script is a block that would be inlined). The `break` rules are skipped inside `while`/`inline_script`, where the stop is not local to the block. A `break` that ends the `else` of a chain is dropped when the chain is the last thing in its block (the closing brace already stops it - `leviathans_events_2.txt` line 4232) and kept when script follows, which the `break` really does skip. A `break` also unwinds *through* the scope blocks and the transparent containers around it - only `while`/`inline_script` capture it - so every rewrite that treats the following script as the else side requires each container between that list and a fresh effect execution to end with the conditional's node (`_is_last_script`). That boundary is `EFFECT_ROOTS` - its own set, deliberately not `EFFECT_CONTEXT_SCOPES`: the containers a `break` passes straight through are simply absent from it (`hidden_effect`, the weighted blocks, `random_list`/`random`/`then`), and so are the loops and scripts that capture it instead (`BREAK_CAPTURE_KEYS`: `while`, `inline_script`, which clear the flag outright). A missing key only makes the check stricter, which is the safe direction. Without that the `break` reaches past the list being rewritten: the one inside `overlord = { ... }` in `marauder_events.txt` line 9675 also skips the `country_event` behind the enclosing `if`, and moving it into an `else` would fire that event twice. A run of `break` conditionals becomes the chain's links and, when script follows the run, that script moves into an `else` for the chain - it is what runs when no branch matched (`precursor_events.txt`). A `break` whose conditional is followed by `else_if`/`else` sits in a chain already, so the chain is never wrapped: with nothing behind it the `break` is simply redundant (`crisis_events_2.txt` line 2092), and with script behind it the chain moves under an `else` with its leading `else_if` rebased to an `if` - a bare `else_if` inside an `else` would have no `if` to belong to. A lone `break` in an otherwise empty body is a guard instead: its condition is negated onto the following script, and the following conditional never becomes an `else_if` (script behind that `else_if` would then run even when the guard held) - `horizonsignal_events.txt` line 685. An `else` behind such a guard is that following script, so the pair becomes one inverted `if` holding the else's body (and anything behind the else), rather than an empty `if` plus an `else` - `horizonsignal_events.txt` akx.9470.
- A trigger `if = { limit = L body }` is `L implies body`, i.e. `OR = { NOT = { L } body }`. A limit that is already a negation is negated through its positive form (`_get_positive_form`), so `limit = { NOR = { ... } }` yields the `OR` the `NOR` denies and the rewrite never stacks `NOT` on `NOT`, `NOT` on `NOR`, or a `NAND` on a `NAND` (`00_agreement_term_values.txt` line 879; `_if_implication_node` takes `guaranteed_scopes` for that, so a negation pushed into a scope is only unwrapped where the scope is known to exist). The OR-factoring has two halves: `_factor_or_ands` merges AND siblings that share leaves into one `AND` with the differing leaves in a nested `OR` (`OR = { AND = {A B C} AND = {A B D} }` -> `AND = {A B OR = {C D}}`), which is distributivity and always sound, so it runs even where the hoist is blocked - that is what the `OR` the negated limit folds into needs (`00_agreement_term_values.txt` line 879). Hoisting those conditions *out* of the `OR` into the surrounding list is the half that is guarded by the conjunctive-list test (`GUARD_INHERIT_BLOCKED` plus the quantifier prefixes): inside an `OR`/`NOR`/`NOT` the siblings are ORed, so the hoist would turn `o AND t AND (r1 or r2)` into `o OR t OR …`. Both build on `_extract_common_and_children`, which walks the first block's children in order instead of iterating the fingerprint set: a set orders its items by hash, string hashing is randomized per process, and the same input would then come out with the leaves in a different order on every run.
- A safe-navigation `?` node is never negated: `NOT = { X? = { C } }` stays as written, because `not(E and C)` is not `E and not C`. Inside `NAND`/`NOT` that guard fold *is* allowed (`GUARD_FOLD_NEGATED_AND`): those containers AND their children and negate the whole, and a `?` block keeps the existence inside that same conjunction - `NAND = { exists = X  X = { C } }` and `NAND = { X? = { C } }` both read `not(E and C)`. `GUARD_INHERIT_BLOCKED` keeps `NAND` for the *inheritance* rule alone (an `exists` in there proves nothing about its siblings). The two-child shape still ends up as `NOT = { X? = { C } }` (the fold leaves one child and a one-child `NAND` is a `NOT`), and without safe navigation it expands into `OR = { NOT = { exists = X } X = { not C } }` (or stays as written when the block cannot be negated). It never collapses to `X? = { not C }` - that is what the expansion is for - and `NOT = { exists = X  X = { C } }` folds the same way instead of falling through to the NOR→block repair, which used to hand back `X? = { not C }` (both sides negated). The push-in of a negation into a plain scope block (`NOT = { X = { C } }` → `X = { not C }`) is untouched. A `NOT` that holds a `?` block is still a negation for the merges, though, because its positive form *is* its child list - the `?` node already means `E and C`, and a NAND child means "and this", so `if = { limit = { root? = { is_ai = yes } } root = { is_at_war = no } }` folds into `NAND = { root? = { is_ai = yes }  root = { is_at_war = yes } }` instead of staying the `OR` the implication rewrite built (`00_rules.txt`, `can_declare_war`); the empty positive form that used to delete the whole condition was the bug, not the merge.
- A lone `if` as the *only* child of an effect iterator dissolves into that iterator: `every_country = { if = { limit = L body } }` is `every_country = { limit = L body }`, since the iterator's own `limit` means exactly the same. Gated by `CONDITIONAL_CONVERSIONS`; the key must start with `EFFECT_QUANTIFIER` and not be in `EFFECT_ITERATOR_NON_SCOPES` (`random_list`, `random_weight`, `random_names`, `random_events` - weight tables and name/event lists that share the `random_` prefix and take no `limit`), an `if` with an `else` is left alone, and the `if`'s comments move onto the limit resp. the last body node.
- A negated block trigger that compares a number negates **on that comparison** and keeps its selector: `NOT = { has_resource = { type = volatile_motes amount > 0 } }` becomes `has_resource = { type = volatile_motes amount <= 0 }` (`02_scripted_triggers_federations.txt`). The flippable child keys are `value`, `count` and `amount` (in `_negate_numerical_comparison_recursively`, Case 2); the `num_*`/`count_*` special cases and the single-child recursion are unchanged, and the dry run still refuses to produce `!=`.
- The safe-navigation guard fold (`exists = xyz` + `xyz = { ... }` → `xyz? = { ... }`) walks past comments, plain positive leaves *and* whole trigger blocks, up to three such conditions; a block only stops the scan when `_uses_scope_as_value` says it touches the guard's scope, and a negated leaf (`= no`) stops it as well. `exists = from` + `species = { ... }` + `from = { ... }` therefore folds (`00_rules.txt`, `should_hide_pop_group_size`): the siblings of a trigger list are independent conjuncts, the guard gates none of them, and the folded block re-asserts the existence itself.
- Trigger/effect evidence is positive-only, and the safe-navigation `if` fold needs it. `_body_scan_hint`/`_body_node_hint` accept `_is_known_scope` (dotted paths matched link by link and macros stripped, so `root.owner` and `event_target:sys_$SIZE$` count) plus the trigger/effect prefixes and containers (`uses_`/`is_using_` are trigger evidence; `custom_tooltip` is a trigger container - 1835 trigger bodies, 0 effect verbs in 4.4 - while `tooltip` is the effect one; an `if`/`else_if`/`else` node is transparent with its `limit` skipped), and an unknown leaf proves nothing. `if = { limit = { exists = xyz } xyz = { ... } }` therefore only folds into `xyz? = { ... }` when the body *proves* effect script: trigger evidence keeps the `if` for the `OR` rule, ambiguity leaves it exactly as written (`00_rules.txt`). The old rule folded anything that was not provably trigger, i.e. it read the absence of trigger evidence as proof of effect.
- The conditional conversions are ON by default in the module and in a bare `python bin/logic_optimizer.py` run (other tools import the script as a library), so the VS Code extension - the one place they default to off - now says so explicitly with `--no-conditional-conversions`. Before, the CLI kept them off unless `--conditional-conversions` was passed, which contradicted the README ("the standalone script defaults the conversions on") and made a bare script run look like it did nothing on an already-formatted file.
- The `exactly one` fold (`CALC_TRUE_IF_CONVERSIONS` / `--calc-true-if-conversions` / `--no-calc-true-if-conversions` / `paradox-formatter.calcTrueIfConversions`) is a switch of its own, apart from `CONDITIONAL_CONVERSIONS`: it is the only rewrite that *creates* a counted trigger rather than re-spelling conditionals that are already there. `CALC_TRUE_IF_CONVERSIONS` gates both of its entry points - the `OR`/`NOR` arm scan (`_xor_to_calc_true_if`/`_xor_to_or_nand`) and the trigger `if`/`else` spelling (`_trigger_if_else_xor`) - and the shared loop, whose if/else fold stays behind `CONDITIONAL_CONVERSIONS` (it `continue`s past the XOR attempt when that is off). Also on by default here, for the same reason as the group above; the extension keeps it off (`--no-calc-true-if-conversions`) unless its setting is on. With it off the `OR` it would claim falls through to the `OR` → `if`/`else` rule, so an `exactly one` written as `OR` arms still folds when only `conditionalConversions` is on, and it is left as written when both are off.
- `XOR_FORM` / `--xor-form` / `paradox-formatter.xorForm` picks how a fully written out `exactly one of {A, B}` (`OR = { AND = { not A B } AND = { A not B } }`) is spelled: `calc_true_if = { amount = 1 A B }` (`amount` is an exact comparison from Stellaris 2.1 on - the 1.9/2.0 tooltips read "If at least $AMOUNT$ ...", 2.1+ interpolate `$COMPARATOR$` - so vanilla only ever writes `amount >= N`), or the version-safe `AND = { OR = { A B } NAND = { A B } }` (`or_nand`, two members only). `calc_true_if` is the default; `or_nand` writes the version-safe `AND = { OR = { A B } NAND = { A B } }` pair instead and `auto` mirrors the file - using the compact form only when the document already writes an `amount >= ...` comparison, the OR/NAND pair otherwise. `_xor_members` requires one `AND` per member, each holding that member positive and every other member negated, with no comments (the sub-structure is dropped) and at most four members. The trigger `if`/`else` spelling of the same expression folds too (`_trigger_if_else_xor`: `if = { limit = { A } B } else = { C }` with `C` the negation of `B` is `amount = 1` when exactly one of `A`/`B` is negated, `amount != 1` when both or neither is - `_positive_member` unwraps the negated side via `_get_positive_form`, which only accepts a node that really is a negation). It stays inside trigger positions (an effect `if`/`else` runs one of two bodies, so it is left alone), and the mode gate falls back to `_body_scan_hint` on the members when the container is unknown.
- A comment run that *follows* the last negation of a merged sequence stays where it is: it describes whatever comes next, not the merged `NAND`/`NOT`. The look-ahead used to swallow it, so `NOT = { ... }` / `# System owned by a player` / `AND = { ... }` ended up with that line *inside* the `NOT` (`02_scripted_triggers_machine_age.txt`). Comments between two merged nodes still travel with the node they precede, and a comment inside a merged block stays inside it.
